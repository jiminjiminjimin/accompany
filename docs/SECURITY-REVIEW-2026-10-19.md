## 1. 종합 판단

**어르신 이름, 주소, 좌표, 승하차장소와 등·하원 기록은 현재 저장 경로에서 Android Keystore 키를 이용한 AES-256-GCM으로 암호화됩니다.** 단순 Base64 변환이나 확장자 변경이 아닙니다. 암호화 대상은 JSON으로 직렬화한 전체 데이터이며, 인증 태그로 변경 여부도 검사합니다.

그러나 이를 “개인정보가 모든 상황에서 보호된다”는 의미로 해석할 수 없습니다. 다음 경계가 중요합니다.

1. 앱 화면과 GPS 서비스에서는 복호화된 데이터가 메모리에 존재합니다.
2. 키 사용에 사용자 인증을 필수로 요구하지 않습니다. 기기가 잠금 해제 상태이거나 화면 잠금이 없으면 앱에 바로 진입합니다.
3. XLSX 내보내기 결과는 암호화되지 않으며, 선택한 문서 제공자가 클라우드일 수도 있습니다.
4. 이번에 확인한 APK는 Android Debug 인증서로 서명된 debuggable 빌드입니다.
5. 현재 어르신·장소를 삭제해도 과거 운행에 보관된 이름·주소·좌표 스냅샷은 남습니다.

저장 암호화의 기본 구현은 확인되지만, 운영 배포 보안과 개인정보 수명주기까지 완료된 상태는 아닙니다. 이 보고서는 인증·침투시험 합격서가 아니며, 미실행 검증 항목을 성공으로 간주하지 않습니다.

## 3. 데이터 흐름과 보관 범위

### 3.1 입력 및 내부 저장

화면 입력·GPS 입력 → 모델 검증 → CareData 및 운행 모델 → UTF-8 JSON → AES-GCM 암호화 → 앱 내부 noBackupFilesDir/care-v1.enc.

조회 시에는 반대로 암호문 전체를 읽고 복호화·JSON 해석 후 Compose 화면 또는 GPS 서비스에 전달합니다. SQLCipher나 암호화 데이터베이스를 사용하지 않으며, 파일 단위 암호화입니다.

| 데이터 | 내부 저장 형태 | 추가 보관 또는 전달 |
| --- | --- | --- |
| 어르신 | ID, 이름 | 운행 대상 스냅샷 및 XLSX에 이름 포함 |
| 승하차장소 | ID, 이름, 주소, 위도·경도 | 운행 스냅샷에 복사 |
| 연결 관계 | 어르신 ID와 장소 ID | 운행 시작 시 선택 대상 고정 |
| 운행 | 방향, 시작·종료 시간, 대상 목록 | 완료 기록 조회 및 XLSX 집계 |
| 도착 추정 | 대상 ID, 장소 ID, estimatedAt, confirmedAt, GPS_DWELL_20S | 내보내기에는 추정 시간 사용 |
| 위치 표본 | 판정 중 메모리에서 사용 | 검토 경로에서 전체 이동 경로 파일 저장 없음 |

전체 원시 경로를 저장하지 않는 점은 데이터 최소화에 해당합니다. 다만 과거 운행의 주소와 좌표까지 보존하므로 현재 목록보다 보관되는 개인정보 범위가 넓습니다.

### 3.2 외부 경계

주소 검색은 Android Geocoder에 입력 주소를 전달합니다. 앱 코드가 이름 필드를 별도로 붙이지는 않지만 사용자가 주소 입력란에 개인정보를 쓰면 함께 전달될 수 있습니다. 실제 서비스 제공자, 서버 저장 정책, 네트워크 암호화 상태는 이 앱의 코드만으로 확정할 수 없습니다. “모든 정보가 기기 밖으로 나가지 않는다”는 표현은 부정확합니다.

XLSX는 시스템 파일 생성 화면을 통해 사용자가 고른 URI에 씁니다. 이름과 날짜·시간이 파일 제공자에 전달되며, 주소·좌표는 현재 XLSX 열에 포함하지 않습니다. 앱 내부 암호화와 백업 제외 설정은 출력된 파일에 적용되지 않습니다.

## 4. 실제 구현된 보안 통제

### 4.1 암호 알고리즘과 키 관리

- `KeyGenerator`의 AndroidKeyStore 제공자를 사용합니다.
- AES 256비트, GCM 모드, NoPadding, 암호화·복호화 용도로 키를 생성합니다.
- 키 별칭은 care-data-v1이며, 앱 코드에 원시 AES 키를 하드코딩하지 않습니다.
- `setRandomizedEncryptionRequired(true)`를 지정하고, 암호화 시 제공자가 생성한 12바이트 IV를 사용합니다. 고정 IV를 재사용하는 코드는 없습니다.
- 파일은 4바이트 CAR1 헤더, 12바이트 IV, 암호문과 인증 태그로 구성됩니다.
- AAD는 고정 문자열 care-schema-1입니다. 복호화는 128비트 GCM 태그를 지정합니다.
- 헤더는 형식 검사 대상이며 AAD 자체에 포함하지 않습니다. 현재 고정 헤더의 불일치는 복호화 전에 거부합니다.

GCM은 키가 보호되는 조건에서 파일 내용의 기밀성과 위변조 탐지를 제공합니다. AAD 문자열은 비밀키나 추가 암호화가 아닙니다. 유효한 과거 암호문 재사용, 정상 앱을 통한 허위 입력, 앱 프로세스를 장악한 공격자의 복호화 호출까지 막지는 않습니다.

Android Keystore 사용과 하드웨어 격리는 동일한 주장이 아닙니다. 코드에는 KeyInfo 보안 수준 조회, StrongBox 요청, 키 증명 검증이 없습니다. TEE 또는 StrongBox에 저장된 키라고 단정할 수 없습니다. 플랫폼 문서도 앱 프로세스가 침해되면 키를 추출하지 못하더라도 해당 앱의 키 사용이 가능할 수 있음을 설명합니다. [Android Keystore 공식 문서](https://developer.android.com/privacy-and-security/keystore)

### 4.2 저장 실패와 데이터 검증

`AtomicFile`로 암호문을 쓰고 fd.sync 및 finishWrite를 수행합니다. 쓰기 예외에서는 failWrite를 호출하며, 저장 후 다시 읽어 원래 모델과 일치하는지 검사합니다. UI와 서비스의 읽기-변경-쓰기는 프로세스 공통 잠금으로 직렬화합니다.

이 구조는 쓰기 중단과 같은 일부 손상 위험을 줄입니다. 다만 저장 완료 뒤 읽기 검증이 실패한 모든 상황에서 이전 데이터가 복원된다고 보장하는 것은 아닙니다. 프로세스 공통 잠금은 다른 프로세스나 루트 수준 파일 변경에 대한 보호 수단도 아닙니다.

ID 중복, 연결 대상 존재, 좌표 유효 범위·유한성, 이름·주소 공백, 동시에 활성 상태인 운행 수 등 모델 불변조건을 검사합니다. 기존 암호문이 있는데 키가 없을 경우 새 키로 조용히 덮어쓰는 대신 실패하도록 구현했습니다.

### 4.3 이전 데이터 마이그레이션

기존 pathreport SharedPreferences의 places 평문을 읽어 암호화 저장하고 재검증한 뒤 기존 항목을 삭제합니다. SHA-256은 마이그레이션 원본 식별과 중복 방지를 위한 해시이며, 암호화나 인증 MAC이 아닙니다.

변환·쓰기·검증·정리 실패 시 기존 평문이 남을 수 있습니다. 이는 데이터 손실 방지를 위한 처리이지만, 따라서 “어떤 상황에서도 평문 파일이 없다”는 코드 주석의 표현은 전체 수명주기를 설명하기에 부정확합니다. 삭제 성공도 저장 매체의 잔여 블록에 대한 안전한 소거를 입증하지 않습니다.

### 4.4 플랫폼·화면 통제

- 내부 noBackupFilesDir 사용 및 allowBackup=false.
- backup_rules와 data_extraction_rules에 백업·기기 이전 제외 설정.
- usesCleartextTraffic=false. 자체 HTTPS 클라이언트나 인증서 고정 구현은 확인되지 않습니다.
- MainActivity에 FLAG_SECURE 적용 및 API 26 이상 Autofill 제외 설정.
- GPS 서비스 exported=false, onBind 반환 null.
- 알림 PendingIntent는 명시적 대상과 immutable 플래그 사용.
- 알림은 일반적인 운행 상태를 표시하며 이름·주소를 넣지 않습니다. 비공개 가시성을 지정합니다.
- 검토한 운영 코드 경로에서 개인정보를 출력하는 로그는 발견하지 못했습니다. OS·외부 제공자·키보드 로그까지 검사한 결과는 아닙니다.

FLAG_SECURE는 지원되는 화면 캡처 경로를 제한하는 설정입니다. 메모리, 접근성 서비스, 외부 카메라, 침해된 OS까지 보호한다는 의미는 아닙니다. 백업 제외 역시 루트 권한·물리 분석에 대한 완전한 유출 방지책으로 해석할 수 없습니다.

## 5. 접근 제어의 실제 의미

현재 허용 조건은 `!manuallyLocked && (!secure || !deviceLocked)`입니다.

| 상태 | 코드 동작 |
| --- | --- |
| 기기 화면 잠금 미설정 | 자동 진입 |
| 기기 잠금 설정됨, 현재 잠금 해제 | 자동 진입 |
| 기기 잠김 | 앱 잠금 화면 표시 |
| 앱에서 수동 잠금 선택 | 잠금 화면 표시, 이미 기기가 열려 있다면 진입 버튼만으로 복귀 |
| 회전 | configChanges 처리로 일반적인 화면 재생성 방지 |
| 홈 이동 후 복귀 | onResume에서 기기 상태에 따라 다시 진입 판단 |

사용자가 요청한 편의 정책이 반영된 동작입니다. 앱 독립 비밀번호, 사용자별 계정, 역할별 권한, 매번 재인증하는 잠금은 아닙니다. 수동 잠금 플래그는 메모리와 savedInstanceState에 있으며 영구 보안 상태가 아닙니다.

기기 인증이 필요한 경로에서는 createConfirmDeviceCredentialIntent 결과를 사용하지만, 복호화 키와 인증 결과가 암호학적으로 결합되어 있지 않습니다. `setUserAuthenticationRequired`, `setUnlockedDeviceRequired`, BiometricPrompt CryptoObject는 사용하지 않습니다. 공식 API가 제공하는 인증 필수 키 설정과 현재 설정은 구분해야 합니다. [KeyGenParameterSpec.Builder](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder)

키에 인증 조건을 단순히 추가하면 잠긴 화면에서도 GPS를 기록하려는 기능과 충돌할 수 있습니다. 개선 시 화면 조회용 개인정보와 백그라운드 기록에 꼭 필요한 데이터·키 사용 범위를 분리하는 설계 검토가 필요합니다.

## 6. 위험 분석

심각도는 이 앱의 개인정보 처리 목적을 기준으로 한 정성 평가입니다. 공격이 재현되었다는 뜻이 아니며, 조건을 명시합니다. 원격 코드 실행이나 일반 앱에 의한 무조건적인 복호화 취약점을 발견했다고 주장하지 않습니다.

### R1. 운영 배포 시 디버그 APK 사용 — 높음, APK 설정 확인

검사한 APK는 debuggable=true이며 Android Debug 인증서로 서명되었습니다. 병합 Manifest에는 디버그 의존성의 PreviewActivity와 androidx.activity.ComponentActivity가 exported=true로 포함됩니다. 공개 액티비티 자체가 개인정보 유출을 입증하지는 않지만 운영에 불필요한 진입점입니다. ProfileInstallReceiver는 DUMP 권한 보호를 받으므로 무권한 호출 가능 대상으로 분류하지 않습니다.

ADB 사용을 승인한 호스트·디버거 등 충분한 접근 권한을 가진 공격자는 앱 UID의 데이터나 실행 중 평문·키 연산에 접근할 여지가 커집니다. 평범한 다른 앱이 APK만으로 키를 얻을 수 있다는 뜻은 아닙니다.

대응: 별도 운영 서명 관리, debuggable=false 릴리스 APK 생성, 최종 병합 Manifest 검사, 디버그 전용 의존성 배제 확인. 난독화는 보조 수단이며 암호화·권한 통제를 대체하지 않습니다.

### R2. 잠금 해제 기기에서 개인정보 조회·내보내기 가능 — 높음, 정책상 확인

잠금 해제된 휴대폰을 넘겨받은 사람 또는 화면 잠금이 없는 기기의 사용자는 앱에서 별도 신원 확인 없이 이름·주소·기록을 조회할 수 있습니다. 수동 잠금은 재인증 장벽이 아닙니다. 사용자 요구와 일치하지만 개인정보 보호 효과는 제한적입니다.

대응: 편의성을 유지할 경우 위험을 명확히 안내하고, 최소한 전체 내보내기·대량 삭제 같은 동작의 재인증 정책을 검토합니다. 기본 설정을 변경하기 전에 백그라운드 운행 요구와 운영 정책을 함께 결정해야 합니다.

### R3. 키 사용에 사용자 인증 조건 없음 — 중간~높음, 공격 조건 의존

앱 프로세스가 후킹·디버깅되거나 앱 UID 수준 실행이 가능한 경우 UI 잠금 여부와 별개로 키 사용과 복호화가 가능합니다. Keystore는 원시 키 보호를 제공하지만 정상 앱 권한으로 수행되는 복호화 요청을 사용자 신원으로 재검증하지 않습니다.

대응: 릴리스 배포 기본 통제부터 적용하고, 고위험 조회·반출과 백그라운드 기록의 권한·키 경계를 분리합니다. 하드웨어 사용 여부는 실기기 KeyInfo로 확인합니다.

### R4. XLSX 평문 반출 및 제공자 경계 — 높음, 구현 확인

출력은 ZipOutputStream 기반 일반 OOXML이며 비밀번호·파일 암호화가 없습니다. 파일 접근자가 이름과 운행 시간을 읽을 수 있습니다. 선택 URI가 외부/클라우드 문서 제공자이면 해당 영역으로 전달됩니다.

좋은 점은 이름을 수식이 아닌 inlineStr로 기록하고 XML 특수문자를 이스케이프한다는 것입니다. 이 경로에서 이름이 = 등으로 시작하더라도 수식 태그로 작성하지 않습니다. 파일 기밀성 보호와 수식 주입 완화는 별개의 통제입니다.

내보내기 결과 콜백은 잠금 상태를 재검사하지 않고 선택 ID의 자료를 읽어 씁니다. 이미 사용자가 시작한 작업이지만, 문서 선택 중 앱이 잠긴 경우에도 민감 작업을 계속 허용할지 정책을 정해야 합니다. 이 조건의 실기기 재현은 미실행입니다.

대응: 평문 반출 안내, 필요한 날짜만 선택, 민감 작업 재인증 여부 결정, 제공자별 저장 정책 수립. 실패 시 불완전 파일이 남을 수 있으므로 정리 및 실패 표시도 검증합니다.

### R5. 삭제와 실제 보존 범위 차이 — 중간, 구현 확인

withoutElder/withoutPlace는 현재 명단과 연결을 제거하지만 과거 trips의 스냅샷은 유지합니다. 과거 기록 정확성을 위한 구조이나, 사용자가 삭제를 모든 개인정보 삭제로 이해하면 기대와 다릅니다. 자동 보존 만료나 전체 비식별화 처리도 확인되지 않습니다.

대응: 목록 삭제와 과거 기록 삭제의 의미를 분리하고, 보존기간 및 내보낸 파일까지 포함한 삭제 정책을 확정합니다. 플래시 매체에서의 물리적 완전 삭제를 단순 파일 삭제로 보장하지 않습니다.

### R6. 마이그레이션 실패 시 평문 잔존 — 중간, 구현 확인

이전 설치에서 평문 SharedPreferences를 사용했던 경우에 한합니다. 암호화 전환이 실패하면 데이터 보호를 위해 평문 원본을 유지합니다. 신규 설치에서 모든 개인정보를 계속 평문 저장한다는 의미는 아닙니다.

대응: 마이그레이션 상태·실패를 운영자가 식별할 수 있게 하고 정리 성공을 검증합니다. 개인정보가 포함된 원본을 로그로 남겨서는 안 됩니다.

### R7. 유효한 과거 암호문으로 되돌리기 방지 없음 — 중간, 조건부 예상

공격자가 앱 내부 파일을 교체할 충분한 권한과 이전 암호문을 확보하고 동일 키가 유지된 경우, 예전 care-v1.enc를 복원하면 GCM 태그는 유효할 수 있습니다. 외부의 단조 카운터·신뢰 가능한 서버 상태 등 최신성 기준이 없습니다.

대응: 기록의 부인방지·최신성 보장이 실제 요구사항인지 먼저 결정합니다. 로컬 파일 내부 버전 숫자만 추가하면 파일 전체 롤백은 막지 못합니다. 루트 수준 공격까지 막는 로컬 전용 보장을 과장해서는 안 됩니다.

### R8. GPS·시간 기록의 진실성 한계 — 중간, 구현 및 조건부 예상

정확도·정차시간·속도·좌표 변화·표본 순서를 검사하지만 Location.isMock 판정이나 위치 증명은 사용하지 않습니다. 모의 위치, GPS 스푸핑, 수동 좌표 오류가 입력 신뢰성에 영향을 줄 수 있습니다. 동일 장소에 연결된 여러 대상이 함께 도착 처리될 수 있어 사람별 실제 승하차 확인과 다릅니다.

체류 판정은 단조 시간을 활용하지만 표시 시각은 wall clock의 영향을 받습니다. XLSX는 기본 시간대를 사용해 운행 시작일과 시간을 표시하므로 기기 시간·시간대 변경이 분류·출력에 영향을 줄 수 있습니다. 신뢰 가능한 외부 시간 검증은 없습니다.

대응: “도착 추정” 표시 유지, 필요 시 운전자 확인 및 변경 이력 도입, 기록 시 시간대 보존 검토. mock 플래그 확인만으로 모든 위치 조작을 차단했다고 주장할 수 없습니다.

### R9. 키 소실 및 복구·가용성 — 중간, 구현 확인

키 소실 시 기존 암호문을 덮어쓰지 않는 처리는 안전하지만, 복구 키나 암호화 백업·복원 기능은 확인되지 않습니다. 앱 삭제, 데이터 초기화, 기기 고장 등에서는 복구가 불가능할 수 있습니다. 평문 XLSX는 전체 원본 데이터와 연결 정보를 복원하는 백업이 아닙니다.

대응: 복구 요구와 개인정보 보호를 함께 정하고, 필요 시 별도 암호화 백업·복원 검증을 설계합니다. 기존 앱과 서명이 다른 APK를 설치하기 위해 무작정 삭제하지 않습니다.

### R10. 크기 제한·메모리·부분 출력 — 낮음~중간, 조건부 예상

전체 데이터를 한 번에 복호화하고 JSON 및 모델·암호문을 메모리에 보관합니다. 저장 때 전체 파일을 다시 쓰며, 장기간 기록 증가나 매우 긴 입력에서 메모리·지연 문제가 생길 수 있습니다. 명시적인 전체 데이터 용량 상한이나 보존기간은 확인되지 않습니다. XLSX 행 수 제한은 있으나 셀 길이 등 모든 뷰어 제한을 검증하지는 않습니다.

실패한 내보내기 파일을 삭제하거나 원자적으로 교체하는 처리는 확인되지 않습니다. 메모리의 문자열·ByteArray를 명시적으로 지우지도 않습니다. 이는 정상 실행 중 평문이 메모리에 존재한다는 사실이며, 곧바로 원격 공격자가 읽을 수 있다는 뜻은 아닙니다.

대응: 현실적인 입력·기록 크기 제한, 대용량 시험, 스트리밍 또는 저장 구조 개선 필요성 평가, 제공자별 실패 파일 처리 검증.
